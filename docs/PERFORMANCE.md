# ZeroCode performance datasheet

> Generated by [`scripts/benchmark.sh`](../scripts/benchmark.sh) against a live
> stack. Raw data: [`benchmarks/data/languages.csv`](../benchmarks/data/languages.csv)
> (per-language) and [`benchmarks/data/throughput.csv`](../benchmarks/data/throughput.csv)
> (saturation sweep). Re-run with `./scripts/benchmark.sh all`.

This sheet answers two questions:

1. **What does each language cost** — CPU, wall time, memory, and compile cost —
   across light / medium / heavy workloads.
2. **Where does the server bottleneck under traffic** — measured by ramping
   concurrency until throughput stops scaling.

---

## TL;DR

- **Two hard ceilings gate throughput**, both small and both default-derived:
  1. **Worker execution = 4 concurrent jobs.** The worker runs a
     `Semaphore(max_parallel)` where `max_parallel` defaults to the CPU count
     (4 here). Throughput scales linearly to concurrency 4, then **collapses**.
  2. **API in-flight = 16 requests.** The API's Postgres pool is
     `max_connections(16)`, and `?wait=true` holds a connection for the whole
     job. Past ~16 simultaneous in-flight submissions the API returns
     **HTTP 500 `db: pool timed out`**.
- **Peak measured throughput on this 4-vCPU box:** ~**37 req/s** for a trivial
  interpreted job, ~**3.4 req/s** for a cache-missed C++ compile. Both peak at
  concurrency 4.
- **The compile cache is the single biggest lever — but only for
  single-binary compiled languages.** C/Go/Rust/Crystal/… cache the compiled
  `/box/prog` and drop from a 1–13 s cold compile to **~0.02–0.1 s** warm.
  **JVM and .NET languages do *not* benefit** (Kotlin, Scala, Clojure, Groovy,
  C#, F# recompile/respawn on *every* submission) and stay expensive
  (0.7–5.4 s each) under sustained traffic.
- **Memory is the per-job pressure that matters at concurrency.** Most jobs are
  <60 MB, but JVM/Pony/compile-heavy peaks hit **113–383 MB** — at 4 concurrent
  Kotlin compiles that's ~1.5 GB, which matters on small nodes.

## Methodology

**Workload.** Every language runs the same deterministic kernel — a modular
hash loop that is impossible for a compiler to fold into a closed form, so the
loop genuinely executes:

```
read N
s = 0
for i in 1..N:  s = (s * 1000003 + i) mod 4294967291
print s
```

All intermediates fit in signed 64-bit, so every language prints the **same**
value for a given N (used as a correctness check). Programs live in
[`benchmarks/programs/compute/`](../benchmarks/programs/compute/).

**Tiers** (workload size via stdin `N`):

| Tier | N | Probes |
|---|---|---|
| easy   | 1 | startup + (cached) compile + I/O — the fixed per-job floor |
| medium | 1,000,000 | runtime / JIT compute |
| hard   | 10,000,000 | sustained CPU; slow interpreters TLE here |

**Cold start vs. warm tiers.** Before the timed tiers, each language is run once
to populate the compile cache; the **cold-start** column is that first run
(compile + spawn, measured against an emptied `compile_artifacts` table). The
easy/medium/hard columns are **run cost** with the compile cache warm — so the
gap between *cold-start* and *easy* is exactly what the compile cache saves.

**Esoteric / niche tier.** Brainfuck, GolfScript, CJam, Vyxal, Jelly, Samarium,
Paradoc, plus Assembly, COBOL, Prolog, SQL, Forth, Verilog, LLVM IR and Pony
can't express the scaling loop cleanly, so they're profiled at the easy tier
only (a fixed "hello"); medium/hard are **N/A**.

**Saturation sweep.** Each request carries a globally unique source (so it
misses both the result cache and the compile cache → real sandbox execution),
fired at rising concurrency. We record throughput and client-side latency
percentiles per level.

### Reading the table

**Compile cache: huge for binaries, useless for JVM/.NET.** Compare *cold* to
*easy*:

- **Single-binary compiled** (C, C++, Go, Rust, D, Obj-C, Ada, Fortran, Pascal,
  Haskell, OCaml, Nim, Crystal, Dart, Swift, V, FreeBASIC): cold compile is
  0.1–13.5 s but warm runs are **~0.02–0.1 s** — a **100–400× drop**. Crystal
  (13.5 s → 0.03 s) and Go (9.3 s → 0.03 s) are the extreme cases. After the
  first submission of a given program, these are effectively free.
- **JVM** (Kotlin 5.3 s, Scala 3.5 s, Clojure 2.1 s, Groovy 0.9 s) and **.NET**
  (C# 0.7 s, F# 1.7 s): *easy ≈ cold* — the cache does **not** help. Their
  compile output isn't the single `/box/prog` the content-addressed cache
  stores, so every submission re-pays compiler + VM startup. **Under traffic
  these are permanently expensive.**

**Slowest at the heavy tier (hard, wall-s):** Bash 27.2, Octave 24.4, Raku 12.3,
PowerShell 9.0, Kotlin 5.4, Scala 3.6, Julia 2.1, R 2.1, Emacs Lisp 2.0,
Python 1.6. Loop-heavy work in shell/array languages is 100–1000× slower than
compiled — Bash at N=1e7 burns 27 CPU-s where C burns 0.05.

**Heaviest memory (peak RSS, MB):** Kotlin 383, Clojure 203, Pony 200,
Scala 181, Racket 132, F# 115, Groovy 113, Julia 111, TypeScript 80, LLVM IR 66.
Most everything else is <60 MB; the Core-7 compiled langs are <10 MB at runtime.

**Heaviest cold compile (s):** Crystal 13.5, Go 9.3, Kotlin 5.7, Scala 3.9,
Nim 2.8, D 2.1, Dart 2.0, F# 1.8, Swift 1.4, Pony 1.2, Haskell 1.1, C++ 0.9.

### What the curve shows

- **Linear scaling to concurrency 4, then the knee.** Throughput rises
  ~proportionally (1→2→4 ≈ 11→21→37 req/s for Python) while latency stays flat —
  the 4 workers are filling up. At concurrency 4 every worker slot is busy:
  **this is peak throughput.**
- **Past 4, it gets *worse*, not flat.** At concurrency 8 Python throughput
  *drops* to 20 req/s and p99 jumps to 2.1 s: 8 CPU-bound jobs are
  time-slicing 4 cores, so each runs slower and the extras queue. Beyond the
  worker's parallelism, added load is pure overhead.
- **Errors start exactly at concurrency 16.** That's the API's
  `max_connections(16)` Postgres pool. With `?wait=true`, each in-flight request
  holds a pooled connection until its job finishes; the 17th+ concurrent request
  waits for a free connection and trips the pool's acquire timeout →
  **`HTTP 500 {"error":"db: pool timed out while waiting for an open
  connection"}`** (confirmed: 50 concurrent requests → 39×200, 11×500).

## Bottlenecks, in priority order

1. **Worker concurrency = `min(CPU count, ZEROCODE_MAX_PARALLEL)` = 4.**
   The primary throughput ceiling. CPU-bound user code is the workload, so the
   sandbox is fundamentally CPU-limited: useful parallelism ≈ core count.
   *Fix:* add cores and/or worker replicas; they scale throughput ~linearly
   (4 → 37 req/s suggests ~9 req/s per core for trivial jobs). Keep
   `ZEROCODE_MAX_PARALLEL ≈ vCPU` — oversubscribing (the conc-8 row) *reduces*
   throughput and inflates tail latency.

2. **API Postgres pool = 16, amplified by `wait=true`.** Caps *in-flight*
   submissions at 16 regardless of worker count; the 17th gets a 500. Because a
   synchronous `wait=true` request occupies a connection for the job's entire
   duration, a few slow jobs (a Kotlin compile, a Bash hard loop) can pin the
   pool. *Fix:* raise `max_connections`; or prefer the **async submit →
   SSE/poll** flow (`POST` returns a token immediately, releasing the
   connection) for high-concurrency clients instead of `wait=true`.

3. **Per-language cost dispersion (capacity depends on the language mix).**
   Sustained per-worker rate ≈ `1 / wall`:
   - Warm compiled (Go/Rust/C, ~0.05 s) → ~20 jobs/s/worker (~80 across 4).
   - JVM (Kotlin ~5.3 s, *never cached*) → ~0.19 jobs/s/worker (~0.75 across 4).
   - Cache-missed C++ compile (~0.9 s) → ~1.1 jobs/s/worker (measured 3.4 at 4).
   A Kotlin-heavy or compile-cache-missing workload saturates the box **~100×
   sooner** than a warm-Go workload. Size for the *slowest expected mix*.

4. **Memory at concurrency.** 4 concurrent Kotlin jobs ≈ 4 × 383 MB ≈ 1.5 GB;
   on this ~0.5 GB-free box that risks `sandbox_failure` (observed
   intermittently on cold JVM startups). Budget `MAX_PARALLEL × peak-job-MB`
   against node RAM, and cap memory-heavy languages with tighter
   `default_limits`.

### Recommended next steps

- For higher throughput: scale **vCPUs + worker replicas** together; set
  `ZEROCODE_MAX_PARALLEL` to the per-worker core count (don't oversubscribe).
- Raise the API DB pool above 16, **or** steer bursty/high-concurrency traffic
  to async submit + SSE so connections aren't held during execution.
- Treat the **compile cache as load-bearing** for compiled languages — it's the
  difference between 9 s and 0.03 s on a Go submission. Investigate extending
  content-addressed caching to JVM/.NET artifacts (`.jar`/`.dll`) to remove
  their per-request recompile.
- For capacity planning, multiply expected RPS by the per-language `wall` from
  the table above for the languages you actually serve.

## Reproduce

```bash
# Per-language complexity profile -> benchmarks/data/languages.csv
./scripts/benchmark.sh bench

# Saturation sweep -> benchmarks/data/throughput.csv
./scripts/benchmark.sh sweep

# Both
API_BASE=http://localhost:8080 ./scripts/benchmark.sh all
```

For honest cold-compile numbers, clear the compile cache first
(`TRUNCATE compile_artifacts;`) and restart the worker so its in-memory cache
is dropped, then run `bench`.
