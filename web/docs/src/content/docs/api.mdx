All endpoints live under `/v1`. ZeroCode runs as an open, unauthenticated
backend — there is no application-layer auth. Restrict access at the
network layer (private subnet, firewall, reverse proxy with auth, VPN).
A per-IP rate limit (`tower_governor`) caps client volume. Errors return
`{ "error": "..." }` with a 4xx/5xx status.

The full OpenAPI 3.1 specification is served at
[`GET /v1/openapi.json`](/v1/openapi.json). ZeroCode does **not** ship
pre-built SDKs; the [Clients & SDKs](/docs/sdks) page covers the
integration options (raw HTTP, generated client via the bundled
`scripts/generate-sdks.sh`, or the playground's hand-written TS client).

<Aside>
  Set `?base64_encoded=true` on `POST` to send `source_code` / `stdin` as
  base64 (handles binary safely). On `GET`, the same flag makes the response's
  `stdout` / `stderr` / `compile_output` base64-encoded.
</Aside>

## Submissions

### `POST /v1/submissions`

Create a submission. Returns a token for polling, or — with `?wait=true` — the
full result inline (up to 30 s server-side timeout).

```json title="request body"
{
  "language_id": 71,
  "source_code": "print('hello')",
  "stdin": "",
  "cpu_time_limit": 5,
  "wall_time_limit": 5,
  "memory_limit_mb": 256,
  "callback_url": "https://example.com/webhook",
  "base64_encoded": false
}
```

Headers:

- `Idempotency-Key: <opaque>` — optional; the server hashes the body (blake3) and
  returns the same `token` for repeated keys within 5 minutes.

Query params:

- `wait=true` — block up to 30 s for terminal status (long-poll over `LISTEN`).
- `base64_encoded=true` — decode `source_code` / `stdin` from base64.

### `GET /v1/submissions/{token}`

Fetch a submission row. Append `?base64_encoded=true` to round-trip outputs
binary-safely.

### `GET /v1/submissions/{token}/stream`

Server-Sent Events stream of the submission's progress. Events:

| event | payload |
|---|---|
| `processing` | (none) — worker started |
| `stdout` | `{"data":"<utf-8 chunk>"}` |
| `stderr` | `{"data":"<utf-8 chunk>"}` |
| `finished` | `{"status":{"kind":"accepted","detail":null}}` |
| `error` | error message text |

The connection closes after `finished`. Browsers' `EventSource` is fine
for this endpoint since no authentication header is required.

### `GET /v1/submissions`

List submissions. Query params: `page`, `per_page` (max 100), `status` filter.

### `POST /v1/submissions/batch`

Submit one program with **1–100 stdin test cases** in a single request.
Each case becomes an independent submission row linked by a shared
`batch_id`. Compiled languages compile once — the compile cache lets every
case after the first skip straight to the run phase — so a 100-case C++
batch costs roughly one compile plus 100 fast runs.

```json title="request body"
{
  "language_id": 52,
  "source_code": "#include <iostream>\nint main(){long long n;std::cin>>n;std::cout<<n*n<<\"\\n\";}",
  "test_cases": [
    { "stdin": "3" },
    { "stdin": "7" },
    { "stdin": "12" }
  ],
  "cpu_time_limit": 15,
  "wall_time_limit": 30,
  "base64_encoded": false
}
```

```json title="response (202)"
{
  "batch_id": "01HX1ABCDEFGHJKMNPQRSTVWXY",
  "count": 3,
  "tokens": ["01HX…A", "01HX…B", "01HX…C"],
  "status": "queued"
}
```

<Aside type="tip">
  Set a generous `wall_time_limit` (e.g. 30) for compiled-language batches —
  the first case pays the cold compile cost; the rest are near-instant.
</Aside>

### `GET /v1/batches/{batch_id}`

Aggregated batch view: one `SubmissionView` per case (same shape as a
single submission) plus a status summary. Poll until
`summary.queued + summary.processing == 0`.

```json title="response"
{
  "batch_id": "01HX1ABCDEFGHJKMNPQRSTVWXY",
  "items": [
    { "token": "01HX…A", "status": {"kind":"accepted"}, "stdout": "9\n",   "time": 0.41 },
    { "token": "01HX…B", "status": {"kind":"accepted"}, "stdout": "49\n",  "time": 0.02 },
    { "token": "01HX…C", "status": {"kind":"accepted"}, "stdout": "144\n", "time": 0.02 }
  ],
  "summary": { "total": 3, "queued": 0, "processing": 0, "accepted": 3, "failed": 0 }
}
```

The browser playground's **Tests** tab is built on these two endpoints —
it adds expected-output comparison, per-case pass/fail verdicts, and an
inline diff entirely client-side.

## Languages

### `GET /v1/languages`

Returns the language registry as a JSON array. Each entry:

```json
{
  "id": 71,
  "name": "Python",
  "version": "3.13",
  "default_limits": { "memory_mb": 256, "cpu_time": 5, "wall_time": 5, "max_pids": 64 }
}
```

20 languages total. Core 7 IDs: 71 Python, 63 Node, 73 Rust, 60 Go, 48 C, 52 C++, 62 Java. The other 13 use IDs 100–106 (Bash, Lua, Perl, Ruby, R, PHP, TypeScript), 120/121 (Kotlin, Scala), 140 (C#), 152 (Swift), 154 (SQL), and 163 (Dart). The full list lives at [`/languages`](/docs/languages/) or `GET /v1/languages`.

## Health

### `GET /v1/health`

Liveness — unauthenticated. Returns `{"status":"ok"}` when the process is up.

### `GET /v1/ready`

Readiness — gates on a DB ping plus queue depth. Unauthenticated.

### `GET /v1/health/languages`

Per-language health and compile-cache warmth. Poll this before committing a
timed exam to the engine. Query param `window_mins` (default 15, max 1440).

```jsonc
{
  "window_mins": 15,
  "healthy": true,
  "languages": [
    { "language_id": 71, "name": "Python", "samples": 65, "warm_ratio": 1.0,
      "p50_wall": 0.045, "p95_wall": 0.062, "fault_ratio": 0.0, "state": "ok" },
    { "language_id": 60, "name": "Go", "samples": 16, "warm_ratio": 0.0,
      "p50_wall": 4.978, "p95_wall": 8.6, "fault_ratio": 0.0, "state": "cold" }
  ]
}
```

| `state` | meaning |
|---|---|
| `ok` | warm and fault-free; latency is steady state |
| `cold` | under half of recent submissions skipped compilation, so first-run solutions are paying a full compile. Expected, not a fault — pre-warm by submitting each solution once |
| `degraded` | engine faults observed in the window. Do not start an exam |
| `no_data` | nothing ran in the window; absence of evidence, not health |

There are no per-language workers — every worker serves every language from one
queue — so language-selective slowness is always compile cost and cache state,
never a sick subset of workers.

### `GET /v1/statuses`

The complete status vocabulary, machine-readable, with `terminal` / `verdict` /
`retryable` per kind. Generated from the same enum the engine dispatches on.
Unauthenticated and not rate-limited, so a client can assert the contract at
startup. See [Status discriminated union](#status-discriminated-union).

### `GET /metrics`

Prometheus exposition. Unauthenticated. Counters for submissions, cache
hits/misses, webhook deliveries; gauges for queue depth and active sandboxes.

## OpenAPI

### `GET /v1/openapi.json`

OpenAPI 3.1 spec generated from `utoipa` annotations. Feed it to
[openapi-generator-cli](https://openapi-generator.tech/) to emit typed SDKs.

## Status discriminated union

The `status` field is `{ "kind": "...", "detail"?: ... }`. Fetch the
authoritative list at runtime from **`GET /v1/statuses`** — it is generated from
the same enum the engine dispatches on, so it cannot drift from this page.

`verdict` marks the statuses that are a judgement about the **submitted code**.
Only those may be graded.

| kind | terminal | verdict | retryable | meaning |
|---|---|---|---|---|
| `queued` | no | – | – | accepted into DB, not yet picked up |
| `processing` | no | – | – | worker has claimed the row |
| `accepted` | yes | yes | no | program exited 0 inside the limits |
| `compile_error` | yes | yes | no | the compile phase exited non-zero; diagnostics in `compile_output` |
| `runtime_error` | yes | yes | no | killed by a signal; `detail` carries the signal name |
| `non_zero_exit` | yes | yes | no | clean exit with a non-zero code |
| `time_limit_exceeded` | yes | yes | no | `detail` is `wall` or `cpu`; the compile phase has its own budget, so this always refers to the program |
| `memory_limit_exceeded` | yes | yes | no | cgroup `memory.oom_kill` fired during the run |
| `output_limit_exceeded` | yes | yes | no | stdout or stderr exceeded the cap |
| `sandbox_failure` | yes | **no** | **yes** | we could not execute the submission — says nothing about the code |
| `internal_error` | yes | **no** | **yes** | any other fault on our side |
| `cancelled` | yes | no | no | cancelled before completion |
| `expired` | yes | no | no | retention window elapsed |

There is no `wrong_answer`: ZeroCode executes, it does not grade. Comparing
`stdout` to expected output is the caller's job.

### The `verdict` flag

Every submission response carries a top-level boolean, so a grader never has to
enumerate the enum:

```python
if not result["verdict"]:
    raise EngineUnavailable(result["status"]["kind"])
```

`verdict: false` means we could not produce a result. The empty `stdout` that
accompanies it must **not** be compared against expected output — doing so
scores a correct program as wrong. Treat any `kind` you do not recognise the
same way.

## Errors

`413 Payload Too Large` — body exceeded 256 KB.
`422 Unprocessable Entity` — JSON parsed but the request shape was invalid.
`429 Too Many Requests` — per-IP `tower_governor` rate-limit exceeded.
`500 Internal Server Error` — DB or sandbox-side bug; check logs.
